# Changelog

All notable changes to StorScale Platform are recorded here, in the [Keep a Changelog](https://keepachangelog.com/) format. The project uses [semantic versioning](https://semver.org/).

## [Unreleased]

### Added
- **A new team's project, from a template** (U.2, R-U.3): an administrator keeps project templates on Administration → **Templates** (`GET /api/templates`, `PUT`/`DELETE /api/templates/{template}`): a project's spec (its checks, limits, pipelines' settings, where it's told of trouble) and a repo in the install's GitLab. **Make a project** (`POST /api/templates/{template}/projects`) takes a name, editors and readers, and a channel: the template's repo is copied into the install's group as the project's own (unlinked from the template's), "{project}" in its files and in the spec becomes the project's name (one commit), the repo gets a token of its own (Developer, `api` and `read_repository`, a year) kept as the project's connection `<project>-repo`, and its pipelines name it. If any step fails, what was made is taken back. The install's GitLab is `templates.gitlab` in the chart (`url`, `group`, and `tokenSecret`, a Secret with key `token` whose token may make projects in the group; read at each use, so a new token needs no restart), `GITLAB_URL`, `GITLAB_GROUP` and `GITLAB_TOKEN` in Compose.
- **The company's shared libraries** (U.2, R-U.4): an administrator names a library on the same page (`PUT /api/libraries/{library}`): a repo in the install's GitLab at a ref (a tag is best). Projects use it without copying it, and hold no token for it: the platform reads it with the install's token for whoever the realm signed in (`GET /api/libraries`, `/api/libraries/{library}`, `/api/libraries/{library}/archive`). A dbt project names it in `packages.yml` by its repo's address, and `storscale.dbt.build` (and a merge request's review) fetches it: its macros and models, and its generic tests, which are the company's shared checks; a pipeline's Python puts it on its path with `storscale.library.use("name")`, a notebook with `buckets_lake.library("name")`. Moving a library to a new ref reaches every project at its next run. dbt packages work at all now (`dbt deps` on a copy of the project; the repo's checkout is read-only).
- The `templates` suite plays GitLab (its API and its repos), and checks it end to end: a project made from a template for alice, its repo copied with a token of its own, its first pipeline run on day one with the company's Python and dbt libraries, and the dbt library moved to its next tag. `storscale test` runs Compose's suites with `--use-aliases` (the suite's GitLab is `test` there).
- **Growing Buckets' drives:** raise `buckets.storage` (`storscale upgrade --set buckets.storage=40Gi`) and the platform operator grows every drive of the pool to it within five minutes, by asking for more on each drive's claim; the storage class must allow volume expansion. Kubernetes never lets a StatefulSet's volume claim templates change, and Buckets' operator stops at the first object it can't apply, so the chart now keeps each pool's claim template as it was made (read from the cluster) and refuses, before anything changes, drives made smaller, a pool's servers, drives or storage class changed, and a pool removed. The operator logs each drive's state (grown, its file system waiting for its server to restart, refused by the storage class).
- **More Buckets pools** (`buckets.pools`): each another set of servers and drives, appended to the BucketsCluster, with its own size and storage class. Buckets writes new objects to the pool with the most free space. Adding one restarts every Buckets server together (a brief outage of S3); a pool can't be removed through the chart.
- **A project told as its bucket fills:** when a project's bucket reaches 80% of its size limit (`limits.storage`, else the install's `limits.project.storage`), its people hear of it where the project's notify says, and again when it's full and Buckets refuses new files; each is resolved as the bucket empties. Buckets as a whole nearing full still goes to the administrators (the BucketsCapacity rules, which the Health page forwards).

## [0.30.0] - 2026-10-23

Platform roles: finance, the governance group and the data-protection approvers become platform roles, and an administrator defines more, given to Keycloak groups; a data product's consumers' custom roles read it; and Buckets 1.20.4, which removes an object's many versions in minutes, not days.

**Upgrading from 0.29.0:** `storscale upgrade --context <cluster> --version 0.30.0`, after a `--dry-run`. The settings' groups (`USAGE_VIEWER_GROUPS`, `PRODUCT_CERTIFIER_GROUPS`, `DELIVERY_APPROVER_GROUPS`) become the built-in platform roles, so nothing changes for anyone. Buckets goes from 1.19.0 to 1.20.4: its servers restart one after another (a single server: a brief outage of S3). Nothing else to set.

### Added
- **Platform roles** (16.1, R16.2): an administrator gives a platform role to Keycloak groups on the Roles page (**Define a platform role**), from four platform permissions: see-all-usage (every project's usage and cost), see-governance (the Governance page), certify-products, and protect-personal (approve deliveries of personal columns, search what was sent about a person, record erasures). Finance, the governance group and the data-protection approvers are the install's own platform roles, made from its settings (`USAGE_VIEWER_GROUPS`, `PRODUCT_CERTIFIER_GROUPS`, `DELIVERY_APPROVER_GROUPS`) as before, so an upgrade changes nothing; administrators have every permission. A change reaches its groups within half a minute and is in the audit log, with the groups. A project can't give a platform role. The `roles` suite checks it.
- **A data product's consumers' custom roles read it** (16.1, R16.3): a consuming project's custom roles that read are named in the producer's policies for the product, under its readers' rules, as the consumer's readers and editors are; a change to them reaches the producer at once.

### Changed
- **Buckets 1.20.4** (was 1.19.0): bucketsd and its operator's chart. Deleting many versions of one object is no longer quadratic (it rewrites the object's metadata once per drive, not once per version), so removing a bucket with a long history, such as the sample traffic's `photos`, takes minutes rather than days; and Buckets' security fixes. **Upgrading:** the Buckets servers restart, one after another (a single server: a brief outage of S3).

### Added
- **Roles of the company's own** (16.1, R16.1–R16.4): an administrator defines a role on the new Administration → **Roles** page (`GET /api/roles`, `PUT`/`DELETE /api/roles/{role}`) from the platform's seventeen permissions: read (as readers do), read-all (every table as it is: no readers' row filters or masks, tagged columns unmasked), write-tables, read-files, write-files, run-pipelines, change-metrics, build, models, call-models, approve, classify, connections, release, see-usage, see-audit, mute-alerts. Editor and reader are shown as the same permissions, built in. A project's Edit page gives a role to people and Keycloak groups as it gives editor and reader (`members[].role`); someone given several has the one that gives the most. The operator puts a role's people in a Keycloak group of the project's (`<project>-role-<name>`), names it in Ranger's policies (tables, readers' row filters and masks, tags' masks, sources, merge requests' branches), Buckets' and the project's Airflow's by its permissions, and records each member's permissions in the project's status, which platformd and semanticd now check in place of "an editor" (each tab and action asks for the permission it needs). A change to a role reaches every project giving it within a minute, and is in the audit log with what it was; a role a project gives can't be removed; a project can't give a role nobody defined (one gone from the file all the same gives nothing, and the project says so). The Access tab says what each role gives, in words. The definitions are kept in the platform's bucket (`roles/roles.json`). The `roles` suite checks it: a steward reading every row unmasked where a reader sees the EU's, masked; what a steward may and may not do; the role narrowed, and every project following. Not yet: platform-wide roles (the governance group and usage viewers are still settings), Superset and the shared Airflow (they follow the platform-wide groups), and a data product's consumers' custom roles.
- **What a model learned from, in the catalog** (15.1, R15.6): `buckets_lake.sql()` learns the tables each query read (Trino's `EXPLAIN (TYPE IO)`), and tags the MLflow run with them (`lake.tables`: those read before it started, and during it); the catalog draws each from the table, at its Iceberg snapshot when the run started, to the model ("trained on"), beside its scorings' tables.

### Changed
- **The dashboards' sample traffic is optional, and off**: the generator the monitoring example runs (overwrites, downloads and failed requests in sample buckets of its own, `photos`, `logs` and `backups`) is the chart's `monitoring.sampleTraffic`, off by default: an install's dashboards show its own traffic. Compose and CI keep it on (`deploy/kind/sample.yaml`). An install that had it keeps its sample buckets until someone removes them. **Upgrading:** the `traffic` deployment goes; to keep it, `--set monitoring.sampleTraffic=true`.
- **The models' templates run on a schedule too**: Airflow's environment for scheduled notebooks has the notebook image's model libraries (scikit-learn, statsmodels, LightGBM, XGBoost, FLAML, MLflow's client, skops), each template's project is a parameter (`STORSCALE_PROJECT` when scheduled), and the platform's SQL route lets a project's pipelines and agents in, as members, for `buckets_lake.sql()`.

### Fixed
- **The sample traffic filled Buckets**: it overwrites sample photos for ever in a versioned bucket with no rule for old versions, so every install's `photos` grew without bound (one filled its drives, 40 GiB, in ten days, with 90,000 old versions of 60 photos). Setup now expires the photos' old versions after a day, on every install that has the bucket, and the `monitoring` suite checks the rule. To free the space at once on an install that's filling: `mc rm --recursive --versions --non-current --force <alias>/photos` (only the old versions; the bucket's 60 photos stay).

### Added
- **A model as an API** (15.1, R15.4): a project's spec names its servings (`serving`: a name, a registered model, and optionally its server's memory and the most rows a call may score), and each answers with the model's approved version at `POST /api/projects/{name}/serving/{serving}/predict` (MLflow's bodies: `dataframe_records`, `dataframe_split` or `instances`; the answer `{predictions, model, version}`). On Kubernetes each serving is a server of the project's own (`model-<project>-<serving>`, from the chart's new `serving.yaml`, in Airflow's image, in the scorings' virtualenv), signed in to the project's MLflow as a Keycloak client of its own (`serving.<project>.<serving>`) that reads the project as its readers do; a network policy lets platformd alone reach it. In Compose one shared server (`serving`) serves every project's, as the pipelines' account. platformd signs the caller in (the web app's session or a Keycloak token), lets the project's people and agents call it, keeps a project to eight calls at a time, and records each call (`model.called`: who, the version, how many rows; never the rows) and each refusal in the audit log. A newly approved version answers within a minute, nobody restarting anything. The Models tab lists the servings, the version each answers with and where to call it. The `serving` suite checks it.
- **Models in the catalog's lineage** (15.1, R15.6): catalog-sync puts each project's registered models in OpenMetadata, as ML models of a service `storscale-mlflow` (`<project>__<model>`): the card as the description, with the approved version, who registered and who approved it, the training run's parameters and the catalog's commit it started from. Each scoring is lineage from its input table (with its Iceberg snapshot at that commit) through the model to its output; a model, or an edge, that's gone is removed. catalog-sync reads them from platformd (`GET /internal/catalog/models`, for the operator's service account), since only platformd reaches MLflow. The `scoring` suite checks the lineage.
- **Notebook templates for the common models** (15.1, R15.7): `churn`, `propensity` and `forecast`, in each person's `work/templates/` as their notebook server starts (a template they've changed or deleted is left alone). Each reads its data with the new `buckets_lake.sql(project, query)` (a DataFrame, through the platform's SQL route, as the person), searches models with FLAML (a classifier on roc_auc; a daily forecast among ARIMA, SARIMAX, Holt-Winters and tree models), logs and registers the best in the project's MLflow, and says what's next: the model's card, its approval, and the scoring spec that uses it. The SQL route answers a script with up to 100,000 rows (the SQL page still shows a thousand). The `jupyterhub` suite now imports each library a notebook needs, and finds the templates.

### Added
- **The API reference and the Python package** (14.3, R14.7, R14.8): `/api/openapi.json` is an OpenAPI 3.1 document of platformd's routes (97 of them), each with what it does: made from the routes in `server.go` and their handlers' comments by a test that fails when a route is added without it (`STORSCALE_UPDATE_OPENAPI=1` writes it), and served to anyone. The account menu's **API reference** page lists them by area, searchable. The `storscale` package (`stack/python`, `pip install "git+https://github.com/StorScale/storscale-platform#subdirectory=stack/python"`) signs in with a token, a service account's client credentials, or a person's name and password (or asks), renews the token, and gives the common calls by name (`projects()`, `sql()`, `start_run()`, `run_log()`, `wait_for_run()`, `search()`, `usage()`, and more) and any route by its operation ID (`call("get_projects_name_usage", name="sales")`); a refusal raises `storscale.Refused` with the platform's reason and request ID. ### Fixed
- **A new install's generated passwords suit Ranger**: the chart made each with `randAlphaNum 32`, which lacks a digit about one time in 280; Ranger then refused every user setup made from `RANGER_PASSWORD` ("at least one uppercase letter, one lowercase letter and one numeric"), and the install never finished. Each now has all three. An install's existing passwords are kept.
- **A cost under a cent shows as one**: usage kept costs to the cent, so a small project's month, and its alert, read 0.00 of 0.00. Costs are kept to a millionth, and an amount under a cent is written to two significant digits (0.000042).

- **Setup steps wait for their database** on Kubernetes: `airflow-init`, `superset-init` and the catalog's migration start once PostgreSQL accepts connections (`wait.py tcp`). On a first install Airflow's often started first, failed, and was tried again.

### Fixed
- **Setup waits for Ranger's API, not its login page.** Ranger's login page answers before its REST API does, and in CI the API went on answering 404 for minutes after, so the first setup step failed on every try. Setup now waits until the API asks for a sign-in (401, unauthenticated, so it never counts toward Ranger's lockout), and Ranger's readiness probe and Compose's healthcheck check the same. On Kubernetes, a Ranger whose API isn't up 20 minutes after it starts is started again (a startup probe).
- **Superset's dashboard and chart cards show their picture.** Superset's frontend asks for those fallback images at `/static/assets/images/...`, without its `/dashboards` root, and the platform answered with its own page. The gateway sends those requests to Superset.
