## The LLM gateway

**What it's for.** Every call the platform makes to a language model goes through one gateway the company controls: a key per project and per agent, each with a monthly budget, a guardrail that stops what may not leave, and a record of every call. Nobody pastes a provider's key into a notebook.

**Who can do it.** Administrators choose and configure the gateway at install time. Projects then use it through budgets ([Budgets and keys](#budgets-and-keys)).

### The two gateways

| `llm.gateway` | What runs | For |
|---|---|---|
| `stub` (the chart's default) | The platform's stand-in (`stack/tools/llm_stub.py`, in the tools image). | CI, labs and installs without a provider. |
| `litellm` | LiteLLM (`llm.litellm.image`, default `ghcr.io/berriai/litellm:v1.106.0`) on the models listed in `llm.litellm.models`, with the provider's key from the Secret `storscale-llm` (key `api_key`). | A company install. |
| `""` | Nothing. | No keys are made, no budgets kept; the Agents tab has no gateway card. |

Either answers inside the install at `http://llm:4000`, with the master key `LLM_MASTER_KEY` (in the Secret `storscale-env`; in Compose, `stack/.env`, default `sk-storscale-local`). platformd reads spend with it and the operator makes keys with it. Compose always runs the stand-in.

**The stand-in** speaks the little of LiteLLM's API the platform uses (`/key/generate`, `/key/delete`, `/key/info`, `/key/list`, `/chat/completions`, `/embeddings`, `/spend/logs`). It answers a question by repeating it ("You asked: ..."), charges 0.01 per 100 characters asked, embeds text by hashing its words into 256 dimensions (so a search finds texts sharing its words, not meaning), and enforces budgets and the guardrail as LiteLLM does. It also answers a flow's model step and a semantic test's question in the shapes they expect, so they run in CI.

**LiteLLM.** Its keys and spend are kept in a database `litellm` on the platform's Postgres, made on first start (the master key is its password). The guardrail is loaded from `llm_guard.py` beside its config. Its models are LiteLLM's `model_list`:

```yaml
llm:
  gateway: litellm
  guardrails: true
  forbiddenTerms: ["Project Falcon", "/acme-\\d+/"]
  litellm:
    models:
      - model_name: default
        litellm_params:
          model: anthropic/claude-opus-5
          api_base: https://<resource>.openai.azure.com/anthropic
          api_key: os.environ/LLM_PROVIDER_KEY
      - model_name: embedding
        litellm_params:
          model: azure/text-embedding-3-small
          api_base: https://<resource>.cognitiveservices.azure.com
          api_version: "2023-05-15"
          api_key: os.environ/LLM_PROVIDER_KEY
```

The platform asks for the model `default` unless told another name, and for `embedding` when it embeds (knowledge banks, the canvas's nearest-passage step). Anthropic's models on Microsoft Foundry answer the Anthropic Messages API at `https://<resource>.openai.azure.com/anthropic`, which LiteLLM's `anthropic` provider speaks: `model: anthropic/<deployment>`, that address as `api_base`.

### How it behaves

- A change to the models, `guardrails`, `forbiddenTerms` or the guardrail's code restarts the gateway (a checksum on its pod).
- The provider's key is read from the Secret with any trailing newline or spaces trimmed.
- The gateway records each call (who asked, the model, tokens, cost, time), never the question or the answer.

### Limits and gotchas

- Without a model named `embedding` in `llm.litellm.models`, knowledge banks can't be built on LiteLLM (it's commented out in the chart's defaults). The stand-in embeds without one.
- The stand-in's answers are the question repeated: good for checking keys, budgets and the guardrail, not for judging a prompt.
- The stand-in keeps keys in a file in an `emptyDir` on Kubernetes (`/state/keys.json`) and in memory in Compose: a restart loses its keys and their spend. The operator makes keys again for every budget it finds missing at the gateway, so spend starts again from zero.

## Budgets and keys

**What it's for.** A spending limit per project and per agent, enforced by the gateway: at the budget, the gateway stops answering that key rather than the bill growing. The keys are made and kept by the platform; nobody handles them.

**Who can do it.** A project's budget is in its spec: administrators on **Edit**, or a release ([History and releases](15-history-and-releases.md)). An agent's budget is part of its registration (editors, with `build`), approved with the agent. Any member sees the spend on the **Agents** tab.

### Set up

**A project's budget**, in USD a month, up to a million:

```json
{
  "apiVersion": "platform.storscale.io/v1alpha1",
  "kind": "Project",
  "metadata": {"name": "retail"},
  "spec": {
    "members": [
      {"group": "engineers", "role": "editor"},
      {"user": "alice", "role": "editor"}
    ],
    "tables": {},
    "llm": {"budget": 20}
  }
}
```

**An agent's budget**: the **LLM budget (USD a month)** field when registering it, or `budget` in its JSON ([Agents](#agents)). 0 or none: no key.

### How it behaves

- **The project's key.** Within a minute of saving, the operator asks the gateway for a key with alias `storscale/<project>`, `max_budget` the budget and a `budget_duration` of `1mo` (spend starts again on the 1st of each month, UTC), and keeps it as the project's connection `<project>-llm` (kind `llm`, added by `platform-operator`), holding `llmKey`, `llmUrl` and `llmBudget`. On Kubernetes, connections are Secrets (`retail-llm`). The **Connections** tab lists it; the key itself is shown nowhere.
- **An agent's key.** Once the agent is approved and has a budget, the operator makes a key with alias `storscale/<project>/agent/<name>` and keeps it beside the agent's secret in its connection `<project>-agent-<name>`. The agent spends against its own budget, not the project's.
- **What uses the project's key**: a flow's model step ([Flows](08-flows.md)), a question app ([Apps](07-dashboards-apps-assistants.md)), a semantic test asked in words ([Metrics](06-metrics-and-terms.md)), knowledge banks (building and searching), and `POST /api/agent/projects/{name}/ask`. Each call names who asked (the gateway's `user`).
- **A changed budget** means a new key: the old one is deleted at the gateway, and a program holding it must read the connection again. Spend starts again on the new key.
- **No budget any more** (the project's taken out, the agent's set to 0, the agent revoked or unapproved): its key is deleted. Keys of the project's that nothing wants any more are swept at each pass.
- **The spend.** The **Agents** tab's **The LLM gateway** card shows each key: "retail: 0.04 of 0.05 spent", with a green, amber (80%) or red (100%) share. An agent's row shows "0.00 of 0.50 USD a month at the gateway". `GET /api/projects/{name}/llm` gives the same: `gateway`, and `uses` (each `who`, `budget`, `spend`, `key`, `share`, `error`).
- **Alerts.** At 80%: "the project has used 80% of its LLM budget (0.04 of 0.05)". At 100%: "the project is at its LLM budget (0.05 of 0.05): the gateway answers it no more this month", with "Raise the budget on the project's settings, or wait for the month." An agent's say "the agent nightly-summary ...". They link to the Agents tab and go where the project's alerts go ([Data quality](05-quality.md)).
- **At the budget** the gateway answers 422 ("Budget has been exceeded!"): the refusal is the gateway's, the same with LiteLLM or the stand-in.
- Model calls also count toward the project's `cost.budget`, if it has one ([Operating the platform](17-operating.md)).
- **Audit log:** a budget change is a `project.saved` entry; an agent's budget is in its `agent.registered` and `agent.approved` entries.

### Limits and gotchas

- `"llm: budget 2000000: USD a month, up to a million"` and `"agents: <name>: budget ...: USD a month, up to a million"` are refused at save.
- "A month" is the calendar month: LiteLLM sets the spend back to nothing at midnight UTC on the 1st. The stand-in doesn't reset spend at all; its keys are made afresh only when a budget changes or it restarts.
- A knowledge bank needs a project budget ("knowledge: a bank is embedded on the project's gateway key: give the project an LLM budget (llm.budget)"); an agent with a prompt needs an agent budget.

See [Lab 16](../guide.md#lab-16-models-through-the-gateway-on-a-budget).

## The guardrail and forbidden terms

**What it's for.** What the platform masks in tables mustn't reach a model through a prompt either, nor may the platform's secrets or the company's own codewords. The guardrail looks at every question before the model does and refuses it, naming what it found and never the value.

**Who can do it.** Administrators turn it on or off and keep the forbidden terms (install settings). It applies to everyone and every key.

### What it refuses

A question (a chat's messages, or text sent to be embedded) is refused when it holds:

| Kind | How it's found |
|---|---|
| a card number | 13 to 19 digits (with spaces or dashes) that pass the Luhn check |
| a national ID | `123-45-6789` |
| a bank account number | an IBAN that passes its mod-97 check |
| an email address | `name@domain.tld` |
| a phone number | ten to fifteen digits written in groups (`+1 (415) 555-0123`, `0171 234 5678`) |
| a gateway key, a GitLab token, a GitHub token, an AWS key, a signed token (JWT), a bearer token, a private key | the platform's secrets by shape |
| a secret by its name | `LLM_MASTER_KEY=...`, `STORSCALE_LLM_KEY`, `STORSCALE_AGENT_SECRET`, or any `*PASSWORD`, `*SECRET`, `*TOKEN`, `*API_KEY` with a value of eight characters or more beside it |
| a term the company keeps in | the install's forbidden terms |

The refusal is HTTP 400, type `guardrail`: "the question holds a card number and an email address, which may not leave the platform; it wasn't sent to the model (the gateway's guardrail)". A refused question costs nothing.

### Set up

```yaml
llm:
  guardrails: true                                  # false: everything goes through
  forbiddenTerms: ["Project Falcon", "/acme-\\d+/"]
```

A word or phrase matches whole, in any case. One between slashes is a pattern (case-insensitive); a pattern that isn't valid is skipped, not the whole list. In Compose: `LLM_GUARDRAILS` (default `true`) and `LLM_FORBIDDEN_TERMS`, one term a line (default `Project Falcon`, which the test suites ask with).

### How it behaves

- The same module (`stack/tools/llm_guard.py`) runs in LiteLLM (a pre-call guardrail, `llm_guard.StorScaleGuardrail`, on by default for every key) and in the stand-in, so the two refuse the same things.
- `buckets_lake.ask()` raises it as "the gateway refused the question: ..."; the agents' runner as "the gateway refused: ..."; a knowledge bank's build stops at the chunk, adding "(mask such values in the source first: a prepare step, or a view)".

### Limits and gotchas

- The guardrail reads text. Mask personal columns before they reach a model step or a bank: a **Prepare** step's **Replace by pattern** on the canvas, or a view ([Flows](08-flows.md), Lab 18 step 3).
- Patterns over-match on purpose: a long run of grouped digits may read as a phone number. Reword, or keep such values out of prompts.
- With `guardrails: false`, nothing is checked, forbidden terms included.

## Model calls

**What it's for.** Who asked what of the models, how much it cost and how long it took, without keeping the questions or answers.

**Who can do it.** The project's editors and administrators. The **Model calls** card shows to members with `build` once a key exists.

### Set up

On the **Agents** tab, the **Model calls** card: pick **last 1 day**, **last 7 days** or **last 31 days**.

API: `GET /api/projects/{name}/llm/calls?days=7` (1 to 31, default 7).

### How it behaves

- It reads the gateway's own spend logs for each of the project's keys (the project's and each agent's).
- The card says the totals (calls, tokens, USD), the top five by who asked and by model, and the latest 50 calls: **When**, **Key** ("the project" or the agent), **Who asked**, **Model** (chat or embeddings), **Tokens**, **Cost**, **Seconds**, and a red pill for a call that didn't succeed. The API gives up to 200 calls, and totals `byDay`, `byUser`, `byModel` and `byWho`.
- "As the gateway records them: the question and the answer are never kept."

### Limits and gotchas

- The API checks the built-in role: a custom role with `build` sees the card but is refused, 403 "the project's editors see its model calls".
- 503 "the platform has no LLM gateway" when `llm.gateway` is empty.

## Asking a model on the project's key

**What it's for.** One question to the model on the project's key, without the key leaving the platform. semanticd's tests in words use it; a script can too.

**Who can do it.** Any member of the project, by their own Keycloak token (a reader included), and its agents.

```bash
curl -s -X POST https://<platform>/api/agent/projects/retail/ask \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"prompt": "Name three reasons a customer returns a jacket."}'
# {"answer": "...", "cost": 0.0123}
```

**How it behaves.** The gateway's guardrail and the project's budget apply; a refusal comes back as it came ("the gateway refused (HTTP 422): Budget has been exceeded! ..."), status 422. **Audit log:** `llm.asked`, with what it cost. A project without a key: 422 "the project has no gateway key: give it an LLM budget (llm.budget in its spec) and the operator makes one".

## Agents

**What it's for.** A program of the project's own (a nightly summary, a triage bot) that reads the project's data with an identity of its own, only the tools it was given, an owner who answers for it, approval by a second person before it may sign in, and a switch that stops it at once. The audit log names it.

**Who can do it.**

| Action | Who |
|---|---|
| Register, change, revoke | Members with `build` (editors). |
| Approve | Members with `approve` (editors), never the one who registered it. |
| See | The project's members, on the **Agents** tab. |

The **Agents** tab shows when the project has tables and the install has the semantic service.

**An agent is a reader of its project.** Once approved, its Keycloak client's service account (`service-account-agent-<project>-<name>`) is put in the project's readers' group. The readers' rules hold for it as for any reader: only the tables readers may read, their row filters and masks, in Trino, in the MCP server's queries, in `buckets_lake.sql()`. It reads the project's MLflow experiments and models but doesn't log or register; it may call the project's served models and search its knowledge banks. It is a member of its own project only.

### Set up

1. **Agents → Register an agent.**
2. **Name** (lowercase letters, digits and dashes, starting with a letter, up to 31 characters) and **What it's for**.
3. **Tools it may use**: pick from the chips. The MCP server's tools, the project's own tools (`tool:<name>`) and its agents with a prompt (`agent:<project>/<name>`). None picked means every tool a reader may use.
4. For an agent the platform runs: a **Schedule** (cron, UTC), and a **Notebook** (a path in the project's repo) or, in its place, **what it's to do** in words (a prompt). Give it an **LLM budget (USD a month)** if it asks a model; a prompt needs one.
5. **Register**. The owner is you. The card says "awaiting approval".
6. Another editor presses **Approve**. The page shows, once: "nightly-summary is approved. Its client is agent-retail-nightly-summary, its secret ... (shown once: give it to the agent now), and it talks to https://<platform>/mcp with a token from Keycloak (client credentials)." Give the secret to the program now; it's not shown again.
7. Within a minute the operator makes its Keycloak client, and its gateway key if it has a budget.

**Revoke** removes it at once (after a confirm: "Revoke nightly-summary? It signs in no more.").

**API** (signed in, with `X-Platform-Request: 1`):

```bash
curl -s -X PUT https://<platform>/api/projects/retail/agents/nightly-summary \
  -H "Authorization: Bearer $TOKEN" -H "X-Platform-Request: 1" -H "Content-Type: application/json" \
  -d '{"description": "sums the day for the team", "tools": ["list_metrics", "query_metrics", "list_alerts"], "budget": 0.5}'
curl -s -X POST https://<platform>/api/projects/retail/agents/nightly-summary/approve -H "Authorization: Bearer $OTHER_EDITORS_TOKEN" -H "X-Platform-Request: 1"
curl -s -X DELETE https://<platform>/api/projects/retail/agents/nightly-summary -H "Authorization: Bearer $TOKEN" -H "X-Platform-Request: 1"
```

`GET /api/projects/{name}/agents` lists them (each with `clientId`, `connection`, `approved`, `mcpUrl`, and `dag` once it runs), the MCP tools, the `grants` the project offers (`tool:` and `agent:`), `canEdit` and `canApprove`. The approval's answer carries `clientId`, `secret`, `mcpUrl` and "The secret is shown once: give it to the agent now. The operator makes its client within a minute."

**The agent's fields**, as the PUT body or an entry of the spec's `agents`:

| Field | What |
|---|---|
| `name` | Taken from the address on the PUT. |
| `description` | What it's for. Changing it doesn't need approval again. |
| `owner` | A person, who answers for it. Default: who registers it. |
| `tools` | MCP tool names, `tool:<name>`, `agent:<project>/<name>`. None: all the MCP server's. |
| `schedule` | Cron, UTC, for an agent the platform runs. |
| `notebook` | A relative path to an `.ipynb` in the project's repo, under the pipelines' path, as `notebooks/nightly.ipynb`. |
| `prompt` | What it's to do, in words, up to 8,000 characters; in place of a notebook. |
| `budget` | USD a month at the gateway, up to a million. 0: no key. |
| `registeredBy`, `registeredAt`, `approvedBy`, `approvedAt` | The platform's, kept as they were on each save; never set by hand. |

### Signing in as the agent

The program gets a token from Keycloak with the client's credentials, and calls the MCP server at `https://<platform>/mcp` with it:

```bash
curl -s https://<platform>/sso/realms/lakehouse/protocol/openid-connect/token \
  -d grant_type=client_credentials -d client_id=agent-retail-nightly-summary -d client_secret=$SECRET
```

The client's tokens carry the MCP server's audience. The same token reads `GET /api/agent/projects/{name}/runs` and `/alerts` (what `list_runs` and `list_alerts` use).

### The MCP server's tools an agent may be given

| Tool | What |
|---|---|
| `list_projects` | The projects it's a member of, its role, whether each has metrics. |
| `list_metrics`, `query_metrics`, `explain_query` | A project's metrics, their values (as the agent, under its rules), the SQL a query would run. |
| `list_terms`, `describe_term`, `search_terms` | The company's business terms. |
| `list_products`, `describe_product`, `query_product` | Data products. |
| `list_runs` | The project's pipelines and latest runs, and the repo's files Airflow couldn't load. Read-only. |
| `list_alerts` | The project's open alerts. Read-only. |
| `search_documents` | A knowledge bank searched by meaning. |
| `list_tools`, `call_tool`, `ask_agent` | The project's own tools and agents ([below](#the-projects-own-tools-and-agents-asking-agents)). Given with a `tool:` or `agent:` grant. |

[Dashboards, apps and assistants](07-dashboards-apps-assistants.md) describes each tool's arguments and answers.

### How it behaves

- **Approval covers** the owner, tools, schedule, notebook, prompt and budget. Changing any of them takes the approval away until another editor approves again; the operator removes its client meanwhile, so it signs in no more. Approving again makes a new secret.
- **Before approval** it has no client: it can't sign in. A tool it wasn't given is refused, naming what it may use: "the agent may use: list_metrics, query_metrics".
- **Revoked**, it leaves the spec, its connection (secret and key) is deleted, its key goes at the gateway, and the operator removes its client at its next pass: its tokens are refused.
- **Audit log:** `agent.registered` ("registered ..." or "changed ...", with the owner, tools and schedule), `agent.approved`, `agent.revoked`, `agent.ran` for each scheduled run, and every query it makes under its own name (Ranger's audit names `agent-retail-nightly-summary`). A refused self-approval is recorded as `agent.approved` with "approving their own".

### Limits and gotchas

- Approving your own: 403 "an agent is approved by an editor other than the one who registered it".
- Missing permission: "the project's editors register its agents (it takes the permission build)"; "the project's editors approve its agents (it takes the permission approve)".
- Refused at save: "agents: name ...: lowercase letters, digits and dashes, starting with a letter"; "agents: x: owner ... isn't a person's name"; "agents: x: tool y: no tool \"y\" (one of ...; or agent:<project>/<name>, or tool:<name> of the project's tools)"; "agents: x: a notebook or a prompt, not both: ..."; "agents: x: a prompt is done by a model through the gateway: give the agent a budget"; "agents: x: a schedule needs something to run: a notebook (a path in the project's repo) or a prompt"; "agents: x: a notebook runs from the project's repo (pipelines.repo), which the project doesn't have".
- Register agents on the Agents tab or through the PUT route. An agent a release's `project.yaml` brings is recorded as registered by whoever planned the release, so someone else approves it; one the project had keeps its approval unless what approval covers changed. An agent added directly in the spec's JSON on **Edit** has no registrant recorded, so the approval's two-person check has nobody to hold the approver against.
- The secret is shown once. Lost: change something approval covers and have it approved again, or revoke and register again.
- An agent sees what a reader sees. If the readers' rules hide a table, the agent can't read it; give readers that table (or a view of it) rather than making the agent something more.

See [Lab 17](../guide.md#lab-17-an-agent-of-the-projects-own), steps 1 to 5.

## Agents with a notebook

**What it's for.** An agent the platform runs on a schedule: a notebook from the project's repo, executed as the agent, with the MCP server and the gateway at hand.

**Who can do it.** As for agents. The project needs a repo (`pipelines.repo`); see [Pipelines and the project's repo](09-pipelines-and-git.md).

### Set up

1. Put the notebook in the repo under the pipelines' path, say `notebooks/nightly_summary.ipynb`:

   ```python
   import buckets_lake
   a = buckets_lake.agent()                                          # the MCP server, as the agent
   revenue = a.call("query_metrics", project="retail", metrics=["revenue"], group_by=["order__region"])
   night = a.call("list_runs", project="retail", limit=10)
   alerts = a.call("list_alerts", project="retail")
   print(buckets_lake.ask(f"Two sentences for the team's chat: revenue by region {revenue}; runs {night['runs']}; alerts {alerts['issues']}"))
   ```

2. Register the agent with its tools, a **Schedule**, the **Notebook** path and a **budget** if it calls `ask()`. Have it approved.

### How it behaves

- Once approved, it's a pipeline of the project's: `agent_<project>_<name>` (dashes as underscores), tagged `agent`, on the **Pipelines** tab within a minute or two, starting from its approval (no catch-up). The Agents tab names the pipeline.
- Each run checks the repo out at the pipelines' ref and runs the notebook with papermill, signed in as the agent: its client and gateway key come from an Airflow connection the operator keeps (`agent_<project>_<name>`), put in the kernel's environment, never in the logs.
- In the kernel, `buckets_lake` is the [pipelines' variant](10-notebooks-and-models.md#the-pipelines-variant) signed in as the agent: `username()` is `service-account-agent-<project>-<name>`, and two more calls:

| Call | What |
|---|---|
| `buckets_lake.agent()` | The MCP server, as the agent. `.tools()` lists the tools it may use; `.call(tool, **args)` gives a tool's result, and raises `PermissionError` naming what it may use when refused. |
| `buckets_lake.ask(prompt, model="default", system=None)` | A model's answer through the gateway, on the agent's key and budget. |

- The executed notebook, outputs and all, is kept and linked from the run on **Pipelines**; **Audit** has `agent.ran` ("ran" or "failed: cell N failed: ...").

### Limits and gotchas

- `agent()` outside an agent's run: "not an agent's run: no STORSCALE_MCP_URL (an agent's notebook runs from its schedule)".
- `ask()` without a budget: "no gateway key: give the agent a budget (its registration) and the operator makes one". At the budget: "the agent is at its LLM budget: the gateway answers it no more this month". Refused by the guardrail: "the gateway refused the question: ...".
- The notebook missing from the repo: "the agent's notebook notebooks/nightly_summary.ipynb isn't in the repo at main".
- Runs aren't retried: a failure waits for the next schedule, or **Run now**.

See [Lab 17](../guide.md#lab-17-an-agent-of-the-projects-own), step 6.

## Agents with a prompt

**What it's for.** An agent with no code: say what it's to do, give it tools and a budget, and the platform's runner does it on the schedule, as the agent.

**Who can do it.** As for agents. No repo needed.

### Set up

Register the agent with its tools, a **Schedule**, a **budget**, and in **Or, in place of a notebook, what it's to do**, the task: *Each morning, read the open alerts and the failed runs, and write a two-sentence summary for the team.* Have it approved.

```json
{
  "name": "triage",
  "description": "sums up the open alerts",
  "owner": "bob",
  "tools": ["list_alerts", "list_runs"],
  "schedule": "0 7 * * *",
  "prompt": "Each morning, read the open alerts and the failed runs, and write a two-sentence summary for the team.",
  "budget": 0.5
}
```

### How it behaves

- Once approved it's a pipeline, `agent_<project>_<name>`, in the project's own Airflow or the shared one.
- Each run signs in as the agent, lists the tools the MCP server gives it, and asks the gateway's `default` model on the agent's key, giving it those tools and a system message ("You are the agent triage of the project retail: ... Use the tools to do the task; each answers as you, under the project's rules. When you're done, answer with your report alone."). Each tool the model asks for is called as the agent and its answer (up to 20,000 characters) given back, until the model answers with its report: at most 8 rounds.
- The run's record is the transcript, kept as a notebook and linked from the run: the task, each tool call with its arguments and answer (marked "(refused)" when it was), and the report. The report is also in the run's log.
- **Audit log:** `agent.ran`, under the agent.

### Limits and gotchas

- "no report after 8 rounds of tools": the model kept calling tools. Narrow the task or the tools.
- "the gateway refused: ..." stops the run: the budget, or the guardrail.
- The prompt is the agent's instructions for every run; a different task is a different agent (or ask it through `ask_agent`, below).

See [Lab 17](../guide.md#lab-17-an-agent-of-the-projects-own), step 7.

## The project's own tools, and agents asking agents

**What it's for.** An agent sometimes needs the company's own systems (the ticketing API) or another agent's skill. A project declares an API's operation as a tool, signed in by one of its connections, so the agent uses the API without ever seeing its token; and an agent with a prompt can be given to another agent as a tool.

**Who can do it.** Tools are declared in the spec (administrators on **Edit**, or a release). Calling a tool: agents given it (`tool:<name>`), and members with `build`. Asking an agent: agents given it (`agent:<project>/<name>`), and any member of its project.

### Set up a tool

1. On **Connections**, add an **API token** connection (its `token`), say `retail-tickets` ([Getting data in](03-data-in.md)).
2. Declare the tool in the spec:

```json
{
  "tools": [
    {
      "name": "open_tickets",
      "description": "The open support tickets about an order.",
      "url": "https://tickets.example.com/api",
      "method": "GET",
      "path": "/orders/{order_id}/tickets",
      "connection": "retail-tickets",
      "parameters": [
        {"name": "order_id", "in": "path", "type": "integer", "required": true, "description": "The order's number"}
      ]
    }
  ]
}
```

| Field | What |
|---|---|
| `name` | Lowercase letters, digits and underscores, starting with a letter, up to 41. |
| `description` | Required: it's how an agent knows when to use it. |
| `url` | The API's address, `https` or `http`, no query or credentials. |
| `method` | `GET`, `POST`, `PUT`, `PATCH` or `DELETE`. |
| `path` | Under the URL, starting with `/`; path parameters in braces. |
| `connection` | One of the project's connections; its `token` is sent as `Authorization: Bearer`. None: no sign-in. |
| `parameters` | Each `name`, `in` (`path`, `query` or `body`), `type` (`string` default, `integer`, `number`, `boolean`), `description`, `required`. Every `{name}` in the path needs a `path` parameter. A `GET` or `DELETE` has no body. |

3. Give it to an agent: `tool:open_tickets` in its tools. Give another agent with a prompt: `agent:retail/triage`. Either grant also gives `list_tools`, and `call_tool` or `ask_agent`.

### How it behaves

- `list_tools(project)` lists the tools the caller may call (with their parameters) and the agents it may ask. `GET /api/agent/projects/{name}/tools`.
- `call_tool(project, tool, arguments)`: the platform builds the request (path parameters escaped, query parameters added, body parameters as a JSON object), adds the connection's token, and calls the API within 30 seconds, following no redirects. The answer is `{"tool", "status", "answer"}`: JSON as it came, or text cut to 20,000 characters. `POST /api/agent/projects/{name}/tools/{tool}/call` with `{"arguments": {...}}`.
- `ask_agent(project, agent, task)`: platformd runs the asked agent's loop as that agent (its client, its key, its tools less `ask_agent`, so asking can't loop) with the task given, for up to ten minutes, and answers `{"agent", "report", "steps", "cost"}`. Only an approved agent with a prompt and a budget can be asked. `POST /api/agent/projects/{name}/agents/{agent}/ask` with `{"task": "..."}`.
- **Audit log:** `tool.called` ("GET /orders/1042/tickets: HTTP 200 in 0.3s", or "failed: ...") under the caller; `agent.asked` ("asked as service-account-agent-retail-triage by service-account-agent-retail-weekly: 2 tool calls, 0.0300 spent"). Refusals: `tool.call`, `agent.ask`.

### Limits and gotchas

- "the project's editors, and the agents given it (tool:open_tickets), call its tools" (403).
- "an agent asks only the agents it's given (agent:retail/triage)" (403); an agent can't ask itself.
- "the project has no agent triage to ask: an approved agent with a prompt and a budget" (404).
- "the tool's connection retail-tickets isn't kept yet: add it on the Connections tab (an API token)" (422).
- "the tool needs order_id", "order_id is a whole number", "the tool has no parameter x" (400): the arguments don't fit.
- An `agent:` grant may name another project's agent, but the MCP server checks the asking agent is a member of that project, and an agent is a member of its own project only: in practice an agent asks its own project's agents.
- The answer goes to the model: an API that returns personal data hands it to the model's context. Choose operations that return what the agent needs.

See [Lab 17](../guide.md#lab-17-an-agent-of-the-projects-own), step 8.

## Knowledge banks

**What it's for.** A project's text, searched by meaning: what customers wrote, the care guide, the returns page. Each passage is embedded through the gateway and kept as a table of the project's, so a person, an assistant, an agent or a canvas step can find the passages closest to a question, under the project's rules, with where each came from.

**Who can do it.**

| Action | Who |
|---|---|
| Declare, change, remove a bank | Members with `build` (editors). |
| Build it | Members with `build`, administrators, and the project's pipelines (on a schedule). |
| Search it | Any member (readers included), and agents with `search_documents`, each under the project's rules on the bank's table. |

**What it needs.** A project LLM budget (it's embedded on the project's key); `files` for a folder of the bucket; `pipelines` for a schedule.

### Set up

On the **Agents** tab, the **Knowledge banks** card: **Add a bank**.

1. **Name** (lowercase letters, digits and underscores, up to 50) and **What it holds**.
2. **Tables**: a table, its **text column**, and its **id column** (cited with each passage). **Add a table** for more.
3. **And/or a folder of the project's bucket**: its `.txt`, `.md` (`.markdown`) and `.html` (`.htm`) files, as `landing/uploads/`.
4. **Build it afresh on a schedule** (cron, UTC), or leave empty to build by hand.
5. **Add**, then **Build**. Nothing is embedded until it's built. The card says "reviews: 90 passages embedded, 0.0009 spent".

Or in the spec:

```json
{
  "llm": {"budget": 5},
  "files": {},
  "pipelines": {"serviceAccount": "airflow-pipelines"},
  "knowledge": [
    {
      "name": "reviews",
      "description": "What customers wrote",
      "tables": [{"table": "uploads_reviews", "column": "text", "id": "review_id"}]
    },
    {
      "name": "manuals",
      "description": "The care guide and the returns page",
      "files": [{"prefix": "landing/uploads/"}],
      "schedule": "0 3 * * *"
    }
  ]
}
```

API: `GET /api/projects/{name}/knowledge`; `PUT /api/projects/{name}/knowledge/{bank}` with the bank's JSON (no `name`: it's the address); `DELETE` the same; `POST .../{bank}/build`; `POST .../{bank}/search` with `{"query": "the zip broke", "k": 5}`.

### How it behaves

- **Building**, as the caller (the editor, or the project's pipelines): each table's `id` and text are read through Trino (up to 20,000 rows a source, nulls skipped), and each file under the folder (up to 2,000 files, 4 MB each; an HTML page's scripts, styles and head dropped and its tags taken out). Each text is cut into chunks of about 1,200 characters, embedded 64 at a time on the project's key (the model `embedding`), and written afresh as the table `knowledge_<bank>` in the project's namespace (`source`, `ref`, `chunk`, `text`, `embedding`). It's an ordinary table of the project's, under its rules. The answer says the table, `chunks`, `files`, `skipped` (files of another kind or too big) and `cost`.
- **Searching**: the question is embedded the same way, and the bank's table is ranked in Trino by cosine similarity, as the person or agent asking. Each hit is `source` (`table.column`, or `files:<folder>`), `ref` (the row's id, or the file's key), `text` and `score` (1 the closest). `k` is 5 by default, up to 50. The card's search box does it; an assistant or agent uses `search_documents(project, bank, query, k)`.
- **On the canvas**, an **Ask a model** step's mode **Nearest passage in a knowledge bank** adds each row's nearest passage and its source as two columns ([Flows](08-flows.md)).
- **On a schedule**, the bank is a pipeline of the project's, `knowledge_<project>_<bank>`, tagged `knowledge`, that asks the platform to build it afresh as the project's pipelines (one retry).
- **Removing** a bank takes it out of the spec; its table `knowledge_<bank>` stays until someone drops it.
- **Audit log:** `knowledge.declared` (its sources and schedule), `knowledge.built` ("90 chunks (0 files), 0.000900 spent"), `knowledge.removed` ("its table knowledge_reviews kept"); a refused build is `knowledge.build`.

### Limits and gotchas

- **The bank's table carries the text of every row its builder could read.** Readers' row filters and masks on the source table don't follow the passages into `knowledge_<bank>`: give the bank's table its own readers' rule ([Access and protection](04-access-and-protection.md)), or build it from a view of what readers may see. If the project lists the tables readers may read, add `knowledge_<bank>` there for readers and agents to search it.
- A source holding an email address, a card number or another masked value stops the build at the guardrail: "embedding chunks 1 to 64: the gateway refused (HTTP 400): the question holds an email address, ... (mask such values in the source first: a prepare step, or a view)".
- "the bank isn't built yet: build it from the project's Knowledge card": search before build.
- "the project has no gateway key yet: give it an LLM budget (llm.budget) and the operator makes one".
- A bank is built afresh each time, not added to: a big source is embedded, and paid for, in full on each build.
- PDFs aren't read: convert them to text or HTML first.
- On the stand-in, search matches shared words, not meaning; LiteLLM's embedding model finds meaning.
- Refused at save: "knowledge 1: a bank's name is lowercase letters, digits and underscores"; "knowledge x: names at least one table's text column, or a folder of files"; "knowledge x, folder 1: a folder of the bucket, ending in /, as landing/docs/"; "knowledge x: files are read from the project's bucket, which it doesn't have (files)"; "knowledge x: on a schedule, the project's pipelines build it: give the project pipelines (pipelines.serviceAccount)".

See [Lab 18](../guide.md#lab-18-what-customers-say-sorted-by-a-model), steps 6 and 7.

## Errors you may meet

| The words | Where | What to do |
|---|---|---|
| "Budget has been exceeded!" (HTTP 422) | the gateway | Raise the budget (a new key is made), or wait for the 1st of the month (UTC). |
| "the question holds ..., which may not leave the platform; it wasn't sent to the model (the gateway's guardrail)" | the gateway | Take the value out, or mask the column first. |
| "the project has no gateway key: give it an LLM budget (llm.budget in its spec) and the operator makes one" | ask, banks | An administrator adds `llm.budget`. |
| "no gateway key: give the agent a budget (its registration) and the operator makes one" | `buckets_lake.ask()` | Give the agent a budget; it's approved again. |
| "the agent may use: ..." | an agent's tool call | Give it the tool (approved again), or use one it has. |
| "an agent is approved by an editor other than the one who registered it" | Approve | Another editor approves. |
| "the project's editors see its model calls" | Model calls | Use the built-in editor role. |
| "no report after 8 rounds of tools" | a prompt agent | Narrow its task or tools. |
| "the bank isn't built yet: build it from the project's Knowledge card" | search | Press **Build**. |
| "the agent triage's client or gateway key isn't kept yet" | `ask_agent` | Wait a minute after approval; check its budget. |
